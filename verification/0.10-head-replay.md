# 0.10 오래된 게시물의 상태 변경 알림 차단

2026-09-26. 사용자 승인으로 운영을 0.10으로 갱신했다. 아래 조사·로컬 검증 절은 배포 전 기록이며 현재 배포 결과는 마지막 절에 추가한다. 실제 Discord 시험은 하지 않았다.

## 확인한 사건과 원인

- 사용자가 이번 알림의 출처로 지정한 ID는 `2102463847714247142`다. 공개 timeline·forecast·feed를 한 묶음으로 읽었고 오류·충돌이 0건이었다. 이 게시물은 일반 리셋 확정이 아니라 `credits`, `banked_state=arriving`으로 정규화됐다. 발표 시각은 `2026-09-22T18:23:37Z`, 즉 9월 23일 03:23:37 KST다.
- Windows의 Wrangler에서 실제 Cloudflare 운영 로그를 읽었다. 2026-09-26T12:05:30Z 기록은 운영 UUID `e81c9de4-800c-4f77-9482-744d85c32493`, 버전 0.9, 5분 Cron, 오류 0건, 알림 0건, `already_seen=21`이었다. 직접 실행이나 시험 발송을 유발하지 않고 기존 Cron을 관찰했다.
- 해당 실행의 `reset`, `reset-sign`, `reset-watch` HEAD는 모두 `2103637477760311522`, 발표 시각 `2026-09-26T00:07:13Z`였다. `banked-sign`, `banked-arriving` HEAD는 9월 23일 게시물이었다. 즉 최신 리셋 HEAD가 과거로 돌아간 것이 아니다.
- 0.9의 `before_source_head` 검사는 `!wasKnown && !active`에만 적용되고 알림 종류별 위치만 비교했다. 이미 기록된 9월 23일 리셋권이 `banked-sign`에서 `banked-arriving`으로 전진하면 9월 26일 리셋 HEAD를 검사하지 않고 발송할 수 있었다. 9월 23일 운영 기록에는 이 ID의 지급 미확인 신호 발송이 남아 있다.
- 이번 발송 순간의 과거 로그·개별 Discord 영수증과 중간 상태 전이 전체는 확보하지 않았다. 정확히 언제 사이트 상태가 바뀌었는지, 직전 단계가 무엇이었는지는 확정하지 않는다. 사용자 제공 출처·현재 공개 구조·현재 운영 HEAD가 우회 경로와 일치하며 아래 재현 시험이 해당 결함을 입증한다.

## 수정 규칙

기존 단계별 HEAD 중 가장 최신 위치를 전체 기준으로 계산한다. 전체 기준보다 오래된 다른 게시물은 기존 ID·활성 상태·상태 전진 여부와 관계없이 보내지 않고 처리 완료로 기록한다. 최신 게시물 자체의 정상 단계 전진은 허용한다. 원래의 영수증, 저장 이름, 운영 namespace, 재시도 및 불확실 전송 보호는 유지한다.

최초 초기화에서 현재 활성으로 제공되는 신호는 기존 규칙대로 한 번 알릴 수 있다. 한 번의 조회에서 여러 새 사건을 처리할 때는 조회 시작 시 저장된 기준을 사용하므로 아직 처리하지 않은 뒤 항목 때문에 앞 항목을 놓치지 않는다.

이는 0.9의 기존 ID 상태 전진 예외를 의도적으로 좁힌다. 더 최근 게시물이 처리된 뒤 오래된 게시물의 실제 리셋권 지급 상태가 바뀌어도 알리지 않는다. 날짜가 오래된 재등장을 막으라는 이번 사용자 요청에 따른 규칙이다.

## 검증과 한계

- Windows / Node.js v24.13.1에서 기존 Git HEAD의 0.9 코드를 별도 로컬 사본으로 실행했다. `September 23 known banked promotion cannot bypass September 26 reset head` 시험은 기대 0건과 달리 모의 Discord 1건을 보내 실패했다. 첫 재현 시 보조 `time.js` 사본이 빠져 시작하지 못했으며, 해당 파일을 추가한 후 실제 판정 실패를 확인했다. 이는 재현 구성 오류와 제품 결함을 구분한 것이다.
- 수정된 코드에서는 같은 재현이 모의 Discord 0건으로 통과한다. 오래된 일반 리셋 확정 차단과 최신 ID의 정상 전진도 함께 검증했다. 기존 활성·이전 버전 이전 시험 4개는 오래된 게시물 허용을 기대하던 항목이므로 새 규칙에 맞춰 변경했다.
- Windows / Node.js의 전체 자동 시험 74개가 통과했다. 포함된 로컬 workerd 시험 5개는 SQLite Durable Object, 동시 요청, 무발송 진단, 발송 보류, 모의 시험 경로를 검증한다. 외부 Discord 전송은 모두 가짜 응답이며 실제 Discord 전달을 증명하지 않는다.
- 최종 후보의 구문·버전 검사와 `wrangler deploy --dry-run` 결과는 아래 최종 확인 절에 기록한다. dry-run은 묶음 생성만 확인하며 실제 Cloudflare의 0.10 실행을 증명하지 않는다.
- 실제 Cloudflare에서는 기존 0.9 상태만 읽었다. 0.10 운영 배포·실제 Discord 시험은 프로젝트의 버전별 승인 규칙 때문에 실행하지 않았다. 별도 무발송 시험판도 아직 배포하지 않았다. 운영에서 수정 효과는 미검증이며 현재 운영 0.9의 결함은 배포 전까지 남는다.

## 운영 적용 대기

이 절은 승인 전 기록이다. 이후 사용자가 운영 배포를 승인했으며 아래 운영 적용 절이 현재 상태다.

사용자의 0.10 운영 적용 승인이 필요하다. 승인 후 기존 Worker와 Durable Object 연결·영수증을 유지한 채 0.10을 배포하고 실제 5분 Cron의 무중복 결과를 확인한다. `/test-discord` 시험 발송은 그 승인에 포함하지 않는다. 기존 Discord 메시지는 수정·삭제하지 않았다.

## 최종 확인

- Windows / Node.js v24.13.1에서 최종 0.10의 `npm run check`와 `npm test`를 다시 실행해 구문·버전 일치 및 **74/74 통과**를 확인했다. 이 중 5개는 같은 Windows의 로컬 workerd 실행이다. 수정 전 재현은 1건 발송, 수정 후 같은 재현은 0건이며 모두 모의 Discord다.
- 버전 변경 직후 1개 시험이 이전 `User-Agent`의 0.9를 고정 기대해 실패했다. 시험을 실제 `MONITOR_VERSION`과 연락 주소를 검사하도록 고친 뒤 위 전체 통과를 확인했다. 실제 공개 API 장애가 아니었다.
- 최종 0.10의 `npx wrangler deploy --dry-run`이 Windows에서 성공했다. 업로드 묶음 38.50 KiB, 기존 운영 연결·5분 주기·시험 꺼짐 설정을 확인했다. 원격 배포는 수행하지 않았으므로 운영 수정 완료를 뜻하지 않는다.
- `git diff --check`를 실행해 공백 오류가 없음을 확인했다. 운영 로그 읽기 프로세스는 종료했다.
- Hive 지식 검토 범위는 `current-project`로 판단했다. 이번 사실은 특정 프로젝트의 판정 수정이며 사용자 전역 선호가 아니다. 현재 프로젝트 등록 범위가 확인되지 않았고 원격 실행 상태는 장기 지식 기록 대상도 아니므로 Hive 정본 기록은 0건이다. 재사용할 코드 규칙과 검증은 이 프로젝트 문서에 남겼다.
